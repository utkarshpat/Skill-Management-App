## Architecture and environment boundary

Use Azure App Service for the React frontend and Node/Express API under one HTTPS origin, Azure SQL Database for structured records, private Blob Storage for attachments, Azure OpenAI for conversational features and Document Intelligence for certificate text extraction. This same-origin packaging needs a small hosting adaptation; current Vercel routing is not portable by copying its configuration.

Request separate UAT and Production resource groups and isolated databases/storage/secrets. Use existing organization landing-zone/network/monitoring resources where they satisfy isolation and residency requirements. A production staging slot is for deployment validation and does not replace isolated UAT data.

Preferred application/data region: Central India, subject to the organization's landing zone. South India is an alternative if co-location with the selected AI model and service availability is preferable. Backups, logs, document processing and DR destinations must also follow the India-only requirement. Do not enable cross-geography AI fallback automatically.

## Read caching requirement — 16 October 2026

The user requested caching to reduce database reads and improve responsiveness. This section is a proposed implementation; no Redis resource or response cache has been installed. The current browser `InflightReads` shares overlapping GET requests only and does not retain completed responses.

Add **Azure Managed Redis** to the infrastructure request, with an approved India-region deployment, isolated UAT/Production data, private connectivity, TLS, managed-identity authentication and memory/eviction monitoring. Confirm subscription region/SKU availability and measured working-set size before choosing capacity. Microsoft recommends Azure Managed Redis for new work as Azure Cache for Redis tiers are retiring: [retirement guidance](https://learn.microsoft.com/en-us/azure/azure-cache-for-redis/retirement-faq), [architecture guidance](https://learn.microsoft.com/en-us/azure/well-architected/service-guides/azure-managed-redis).

Implementation priorities:

1. Cache published catalogue definitions, credential/provider lists and proficiency rubrics first. An initial 5–15-minute TTL is a tuning proposal, combined with versioned invalidation after catalogue approval/publication; TTL alone must not define freshness.
2. Consider 30–60-second caches for expensive Analytics aggregates after profiling and authorization-parity tests. Authenticate and resolve current effective access before lookup and recheck the existing revision contract before response delivery. Cache keys include environment, account, actor, canonical authorized scope, access revision, normalized filters, pagination/sort where applicable, data revision and schema version. Account/scope IDs supplied by a caller never establish authority. A version token must cover all mutations that affect the projection before it can be used for correctness.
3. Keep permission decisions, active status, current-manager/assigned-reviewer checks, writes, export authorization and private-file authorization fresh. Do not cache private attachment bytes or reuse personalized AI answers across people/scopes. Rebuild exports from current authorized data initially. Browser private responses retain the existing HTTP no-store policies; any later in-memory UI cache must clear on session/identity/access changes.
4. Use a cache-aside adapter with bounded TTL/size, in-flight read coalescing and failure isolation. SQL remains authoritative. Redis outages fall back through short timeouts and bounded concurrency; avoid a fallback traffic surge. Misses cannot become permission bypasses or a second durable data store.
5. Invalidate only after committed mutations, including submit/review/renewal, catalogue publication, employee activation/reporting changes and access updates. Cross-instance invalidation needs a durable revision/outbox strategy; transient Redis pub/sub alone is insufficient. Prevent a read started before a mutation from repopulating the new generation with stale data. Date-derived validity also expires at the applicable UTC date boundary even without a write.
6. Measure SQL calls per screen, cache hits/misses, p95 latency, eviction and errors before/after. Test user/account isolation, scoped DENY/revocation, cross-instance writes, stale-fill races, expiry boundaries and Redis outage behavior. Caching should remove expensive projection reads; current authorization rechecks will still incur some SQL reads.

## Current repository work required for migration

1. **Web hosting:** add the production frontend asset serving/SPA fallback and startup packaging, retain `/api` routing, configure `HOST=0.0.0.0` and the platform's port, and exercise deep-link reloads. Current Vercel services configuration does not create this Azure hosting arrangement.
2. **Azure AI parity:** the Azure text provider exists, but currently caps completions at 800 tokens and does not apply the Gemini task-dependent output settings/usage path. Test and adapt tool calling, complete quizzes, structured plans, token budgets and error/429 handling before enabling all AI features.
3. **Certificate autofill:** PDF/image extraction currently depends on the Gemini-specific provider parts. Implement the Azure Document Intelligence text-extraction adapter plus Azure OpenAI field/catalogue matching, with explicit user action, existing file limits and current access rechecks. Provisioning Azure OpenAI alone does not preserve this feature.
4. **Service authentication:** SQL managed identity is supported. Blob adapters currently use a storage connection string, and the Azure AI provider uses an API key. Add the identity-based adapters for an organization enforcing keyless access; Key Vault references are an interim option only if policy permits shared/API keys.
5. **Background reminders:** reminder milestones are currently evaluated when notification feeds are read. Implement a background worker with durable deduplication for credential/version, expiry and milestone, then activate the timer and test 14/10/7/5/3/0-day behavior. Existing in-app notifications do not imply email/Teams delivery; that channel needs its own approved integration.
6. **Organization identity/data:** map organization tenant/object IDs and current employee/reporting data through the existing provider boundary. The real upstream directory adapter and synchronization remain work. Request the internal API contract, authentication method, sample payload, network path, update/deactivation rules and owner. Do not infer application permissions from job titles or employee API role fields.
7. **Cutover and operations:** create a clean organization environment; import only approved catalogue/configuration/real data. Existing demo people and synthetic QA qualifications must be excluded from the employee production portfolio. Rehearse schema/runtime-principal mapping, private file migration, recovery, real SSO and negative access tests. Disable demo login on the official deployment and retire old hosting/secrets only after acceptance and rollback readiness.
