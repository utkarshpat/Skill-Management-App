# Project review and bug findings — 9 October 2026

Status update: the six findings below describe the original implementation. The subsequent certification refinement replaces its browser-only storage and simulated extraction, adds authenticated SQL records/current assigned-manager review, locks submitted/approved details, and derives expiry separately. See `docs/SKILLS_CERTIFICATIONS_REFINEMENT.md` for the code changes and release gate. Migration 053 is installed on `skill-management-dev` and rollback SQL integration passed on 9 October 2026; hosted deployment and authenticated browser acceptance remain pending.

## Project model

The repository is an npm workspace containing a React/TypeScript/Vite SPA and an Express modular monolith. Vercel routes same-origin `/api/*` requests to the API. Microsoft delegated tokens or explicitly gated demo sessions resolve an authenticated person. Access decisions distinguish action, scope, relationship and workflow constraints. Restricted Azure SQL procedures enforce persisted business operations, revision checks and audit. Blob storage holds private skill evidence; Gemini supplies bounded answers and drafts through server-owned tools and budgets.

Business modules are identity, access, organization, skills, learning, recommendations, workflows, dashboard and AI. Knowledge Transfer is a separately switchable temporary feature. Skills connect published versioned catalogue definitions to employee-owned claims and exact assigned current-manager reviews. Learning completion does not establish proficiency; recommendation acceptance creates an employee-reviewed plan. Requests/incidents use participant-scoped lifecycle operations. Dashboard, sidebar and AI discovery project effective access rather than confer it.

Certifications is an exception to that architecture: the accessible SPA screen uses bundled example records and browser localStorage, without a corresponding certification API/store/procedure or action registry. Its polished UI currently presents simulated persistence, review and extraction as operational capabilities.

## Confirmed findings

### 1. P1 — Certification review authority is inferred from role names and unrelated capabilities

Locations: `apps/web/src/certifications/Certifications.tsx:41`, `:51`, `:152`, `:210`, `:531`; `apps/api/src/modules/access/workspace.ts:33`.

A person with a role containing `manager` or `lead` receives the verification queue even when `reviewSkills` is false. Administration or catalogue management also unlock organization directory/review controls. Queue filtering checks only `SUBMITTED`; it does not check current direct reports, assigned reviewer or self-review. A manager's own submitted record also receives a Verify button in My Certifications. The decision writes `verified: true` locally without any server recheck.

Reproduce: give an own-profile person an otherwise unprivileged role named `Team Lead` and open `/certifications`. The queue displays all bundled submitted records. Approve an unrelated person's record or submit and approve the manager's own credential.

Impact: the UI offers and records verification outside the approved authority contract. This is a client-side certification defect; it does not establish a bypass of the existing SQL skill-review procedures.

Fix: keep certification review unavailable until a separate implemented certification action/resource contract and backend persistence exist. Resolve reviewers and scope on the server, enforce deny/active/state/revision rules, and use canonical decisions in the UI. Do not reuse a role name or unrelated capability as authority.

### 2. P1 — Submissions and reviews are isolated to one browser and shared between signed-in identities on that browser

Locations: `apps/web/src/certifications/initial-data.ts:269`, `:283`; `apps/web/src/certifications/Certifications.tsx:105`, `:192`.

Every user/account uses `cil.certifications.v1`. Save/submit/review only updates that localStorage entry. There is no transmission to an assigned reviewer and no server audit. Another browser starts from bundled fixtures rather than submitted records. Switching accounts on the same origin retains the prior browser's data, which directory/queue views can expose.

Reproduce: submit a new credential in browser A, then open the review queue in browser B. The submission is absent. Sign out and switch identities in A; the stored collection remains.

Fix: persist actor/account-bound records through authenticated API and SQL transactions. If retaining a prototype, explicitly mark it as simulated, isolate storage by account/person, and avoid claiming that submission reached a reviewer.

### 3. P1 — Editing an approved credential preserves its verification on changed facts

Locations: `apps/web/src/certifications/Certifications.tsx:541`; `apps/web/src/certifications/CertificationDialog.tsx:128`, `:157`.

Approved records receive an Edit button, including the owner's approved records. Saving changed certification name, issuer, dates or credential URL without resubmitting preserves `initial.status === 'APPROVED'` and `initial.verified === true`. Rebuilding the record also drops reviewer name/date and feedback.

Reproduce: edit an approved credential, replace its title/link, and select Save Draft. The replacement remains APPROVED and verified, while its review provenance disappears.

Fix: lock reviewed fields or create a new unverified draft/revision requiring a fresh review. Preserve historical review provenance separately and enforce transitions in the backend.

### 4. P1 — AI scan and badge fetch fabricate credential facts

Locations: `apps/web/src/certifications/ai-extractor.ts:10`, `:101`; `apps/web/src/certifications/CertificationDialog.tsx:84`, `:117`.

Document extraction reads only `file.name`; it never reads the uploaded bytes. URL extraction uses substring checks and never fetches the resource. Both invent issue/expiry dates, credential IDs and confidence scores. The dialog presents these as AI-extracted facts and a verified fetched badge.

Runtime reproduction: a stub named `aws.pdf` whose content accessor would throw returned AWS metadata with 97% confidence without reading content. `https://invalid.example/credly.com/aws` returned AWS metadata with 99% confidence without fetching anything.

Fix: disable or explicitly label simulation. Actual extraction must use document content or validated issuer metadata, retain unknown fields as unknown, and never represent generated guesses as verification.

### 5. P2 — Approving an expired credential makes it active

Location: `apps/web/src/certifications/Certifications.tsx:220`.

Approval unconditionally sets `active: 'Y'`, regardless of `expiryDate`. Thus an expired submission becomes Active & Valid and enters active exports after approval. Validity also does not automatically update as stored records expire.

Reproduce: submit a credential with an expiry date in the past; approve it in a manager queue. Its active flag changes from N to Y despite the unchanged expiry date.

Fix: derive current validity from expiry and the applicable calendar date independently of review status. Approval must not overwrite expiry-derived validity.

### 6. P2 — Failed storage writes are reported as successful saves

Locations: `apps/web/src/certifications/initial-data.ts:283`; `apps/web/src/certifications/Certifications.tsx:105`, `:203`.

`saveStoredCertifications` catches quota/disabled-storage errors and returns normally. The caller already updates in-memory state and subsequently shows success. The dialog closes; reload loses the apparently saved submission or review.

Runtime reproduction: replace `localStorage.setItem` with a function that throws a quota error; saving returns normally. The error cannot reach the caller.

Fix: propagate a failure or return an explicit result. Commit UI state and show success only after persistence succeeds; keep the draft open on failure.

## Recommended order

First remove misleading verification and extraction claims or gate this prototype. Then implement the certification action/resource contract and shared server persistence before enabling reviews. Add focused tests for cross-person/self-review denial, approved-record changes, expired approvals, failed persistence and extraction provenance. Passing current suites does not cover these flows.
